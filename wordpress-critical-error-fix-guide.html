Why WordPress Throws the "Critical Error" Message

Starting in WordPress 5.2, WordPress stopped showing raw PHP error stacks directly on screen to protect sensitive database credentials and file paths from hackers. Instead, it displays the generic message:

"There has been a critical error on this website. Please check your site admin email inbox for instructions."

Under the hood, this is almost always triggered by one of 4 root causes:

  • Plugin Conflicts: A recently updated plugin that uses PHP functions unsupported by your server or has syntax errors.
  • PHP Memory Limit Exhaustion: Heavy plugins (WooCommerce, Elementor, WPML) exceeding your server's assigned memory limit.
  • Theme Functions.php Syntax Error: A missing semicolon or incompatible hook in your child theme.
  • PHP Version Mismatch: Upgrading to PHP 8.2 or 8.3 while running legacy plugins written for PHP 7.4.

Step 1: Enable WP_DEBUG to Reveal the Hidden Fatal Error

Never try to guess which plugin is broken. Let WordPress tell you the exact file and line number:

  1. Log in to your hosting control panel (cPanel, Hostinger hPanel, Plesk) or connect via FTP (FileZilla).
  2. Navigate to your root directory (usually public_html/).
  3. Open the wp-config.php file in an editor.
  4. Find the line that says define('WP_DEBUG', false); and replace it with:
// Turn on WordPress Debugging & Log Errors to File
define( 'WP_DEBUG', true );
define( 'WP_DEBUG_LOG', true );
define( 'WP_DEBUG_DISPLAY', false );
@ini_set( 'display_errors', 0 );

Save the file. Now, visit your website once to trigger the error, then look inside /wp-content/debug.log. At the very bottom of the file, you will find an entry like:

[26-Nov-2026 08:14:22 UTC] PHP Fatal error: Uncaught Error: Call to undefined function get_current_screen() in /home/user/public_html/wp-content/plugins/broken-plugin/init.php:142

Diagnosis complete: The log tells you exactly which plugin (in this example, broken-plugin) and which file triggered the fatal crash.

Step 2: Disable the Broken Plugin via FTP / File Manager

Since the WordPress admin dashboard (/wp-admin) is likely inaccessible, you can disable the offending plugin instantly without database access:

  1. In your FTP or File Manager, navigate to /wp-content/plugins/.
  2. Locate the directory of the broken plugin identified in Step 1.
  3. Rename the folder from broken-plugin to broken-plugin-deactivated.
  4. Refresh your website. WordPress will automatically fail to load that plugin and immediately restore your site!

Pro Tip: If you don't have access to debug logs, you can test if plugins are the culprit by temporarily renaming the entire /plugins directory to /plugins-temp. If the site loads, one of the plugins was the cause.

Step 3: Increase the PHP Memory Limit

If your error log reports Fatal error: Allowed memory size of 134217728 bytes exhausted, your website has run out of memory. To fix this:

Add the following code to wp-config.php just above the line that says /* That's all, stop editing! Happy publishing. */:

define( 'WP_MEMORY_LIMIT', '512M' );
define( 'WP_MAX_MEMORY_LIMIT', '512M' );

If your host restricts wp-config.php overrides, create or edit the .user.ini or php.ini file in your root folder and append:

memory_limit = 512M
upload_max_filesize = 64M
post_max_size = 64M
max_execution_time = 300

Step 4: Fix Corrupted .htaccess Rewrite Rules

Security plugins or rogue redirects can corrupt your .htaccess file, generating 500 Internal Server Errors and critical halts. To reset it to clean default WordPress rules:

  1. Rename your current .htaccess to .htaccess-backup.
  2. Create a new blank .htaccess file and paste the official WordPress rewrite block:
# BEGIN WordPress
<IfModule mod_rewrite.c>
RewriteEngine On
RewriteBase /
RewriteRule ^index\.php$ - [L]
RewriteCond %{REQUEST_FILENAME} !-f
RewriteCond %{REQUEST_FILENAME} !-d
RewriteRule . /index.php [L]
</IfModule>
# END WordPress

Step 5: Run Automated Database Repair

If a server crash or database timeout corrupted core WordPress tables (like wp_posts or wp_options), enable WordPress's built-in repair utility:

define( 'WP_ALLOW_REPAIR', true );

Add this to wp-config.php, then visit https://yourdomain.com/wp-admin/maint/repair.php in your browser. Click "Repair and Optimize Database". Once completed, remove the line from wp-config.php for security.
